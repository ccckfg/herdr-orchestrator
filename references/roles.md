# 角色、kind 与任务卡

## 内置角色

定义在 `scripts/orchlib/config.py` 的 `ROLE_LIBRARY`，要加角色改那里。

| 角色 | 默认模式 | kind 优先级 | 干什么 |
| --- | --- | --- | --- |
| `planner` | 只读 | claude → codex → agy | 拆任务、排执行顺序、点风险，不碰代码 |
| `researcher` | 只读 | agy → claude → codex | 查资料、读代码、回答事实问题 |
| `implementer` | **可写** | claude → codex → droid | 真正改代码；single-writer 下全场唯一写入者 |
| `reviewer` | 只读 | codex → agy → claude | 审 diff 或指定文件，只报可执行的问题 |
| `tester` | 只读 | droid → opencode → codex | 跑测试和构建，回报失败用例与复现命令 |
| `docs` | **可写** | claude → agy → codex | 写文档，可写范围限定在文档目录 |

角色名不在表里也能用，默认按**只读**处理，kind 必须显式指定：

```bash
--role probe:droid            # 自定义角色，只读
--role fixer:claude:write     # 自定义角色，可写
```

## 挑 kind 的原则

1. **以 `doctor` 的输出为准**。herdr 支持 24 种 kind，但本机能起来的只有装了 CLI 的那几个。
2. **写的和审的不要同一个 kind**。同一个模型审自己写的代码，价值大打折扣——
   交叉审查的意义就在于换一套训练数据和偏好。
3. **跑测试挑启动快的**，别让一个重型 agent 光启动就花掉半分钟。
4. **别超过 4 个**。窗格会挤，机器会卡，你自己也读不过来。要更多就拆成多轮。

## 任务卡怎么写

子 agent **看不到你的对话、看不到用户说过什么、也问不到你**。卡是它唯一的信息来源。

必须写进卡里的四样：

1. **背景**——为什么做这件事，够它做判断就行，不用抄全部上下文
2. **具体要做什么**——动词开头，可执行，别写"帮忙看看"
3. **判定标准**——什么算做完，什么算没做完
4. **绝对路径**——要它看的文件、要它跑的命令，路径写全

必须避免的三件事：

- ❌ "按我们之前说的做" —— 它不知道之前说了什么
- ❌ "有问题随时问我" —— 它问了你也收不到，最多变成 `blocked` 卡死
- ❌ "把完整结果打印出来" —— 屏幕会截断，结果必须走文件（协议里已经规定）

卡尾的交付协议由 `orch.py card` 自动附加，**不要自己写**。

## 任务卡模板

```markdown
# 任务：<一句话说清目标>

## 背景

<两三句。它需要知道的前提，不是整段对话history。>

## 要做的事

1. <动词开头，可执行>
2. <...>

## 判定标准

- <什么算做完>
- <什么情况算失败，要写进「遗留问题」>

## 相关路径

- `D:\完整\绝对\路径\file.py`
- 跑测试：`uv run pytest tests/`
```

## 常见编排形态

**交叉审查**（最常用）：

```bash
--role impl:claude:write --role reviewer:codex
# impl 改完 → watch → 把 diff 路径写进 reviewer 的卡 → dispatch reviewer
```

注意这是**两轮**：审查者要等实现者写完才有东西可审。
不要在第一轮就同时派出去——审查者会对着空气审。

**多视角并行分析**（一轮就够）：

```bash
--role reviewer:codex --role tester:droid --role researcher:agy
# 三个只读角色同时开工，互不干扰，watch 一次等齐
```

**流水线**（planner 先行）：

```bash
# 第一轮只派 planner，拿到拆解方案
# 第二轮按方案决定起几个执行角色
```

判断标准很简单：**角色之间有依赖就分轮，没依赖就并行**。
`single-writer` 模式下，写入者天然是串行的那一环。
